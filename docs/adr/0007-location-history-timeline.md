# ADR 0007: Location History Timeline

## Status
**Accepted** (2026-11-07)

## Context

Google 지도 타임라인처럼, 사용자가 하루 동안 어디에 머물렀고 어떻게 이동했는지 보여주는 기능이 필요하다.
Google 타임라인 데이터는 기기에만 저장되고 서버에서 받아 올 공식 API 가 없다. 그래서 Maeul 앱이 직접 위치를 수집해 서버로 보낸다.

결정해야 할 것:
- 수집 주기를 어디서 정하고 지킬지
- 원시 좌표를 어떻게 머문 장소(STAY)와 이동(MOVE)으로 나눌지
- 누가 데이터에 접근할 수 있는지

## Decision

1. **수집 주기는 서버 설정이 기준이다.** 기본 1분(`TIMELINE_COLLECTION_INTERVAL`)이다. 앱은 `GET /api/timeline/settings` 로 주기를 받아 수집한다.
   서버는 저장된 기록과 이번에 받은 기록을 합쳐, 서로 `수집 주기 - 허용 오차(기본 5초)` 이상 떨어진 기록만 저장한다. 같은 시각의 기록과 미래 시각(서버 시각 + 1분 초과)의 기록은 버린다.
2. **원시 좌표만 저장하고, 구간은 조회할 때 계산한다.** 시간순 기록에서 중심점 반경(기본 100m) 안에 최소 체류 시간(기본 5분) 이상 머문 구간은 STAY 로 본다. 그 사이 구간은 MOVE 로 보고 경로와 거리 합을 붙인다.
   같은 장소의 STAY 두 개가 최소 체류 시간보다 짧은 튐으로 나뉘면 하나로 합친다.
3. **본인 데이터만 다룬다.** 모든 API 는 JWT 사용자 id 로 범위를 제한한다. 삭제는 복구할 수 없는 hard delete 이다.

## Rationale

- 수집 주기를 서버 설정으로 두면 앱을 다시 배포하지 않고 주기를 바꿀 수 있고, 오래된 앱이 너무 자주 보내도 저장량이 늘지 않는다.
- 구간을 저장하지 않고 조회할 때 계산하면, 반경이나 체류 시간 설정을 바꿨을 때 과거 기록에도 그대로 적용된다. 하루 기록은 1분 주기 기준 최대 1440개라 조회할 때 계산해도 부담이 작다.
- 위치 기록은 민감한 개인정보라 공유 범위를 두지 않고, 사용자가 지울 수 있게 한다.

## Consequences

### 긍정적 영향
- 설정만으로 수집 주기와 구간 기준을 조정할 수 있음
- 오프라인 동안 쌓인 기록을 순서와 상관없이 한 번에 올려도 같은 결과가 나옴

### 부정적 영향
- STAY 에 장소명이나 주소가 없음. 필요하면 앱이 `/api/location` 이나 Tour 데이터와 맞춰 봐야 함
- 같은 사용자의 업로드 두 건이 동시에 들어오면 같은 시각의 기록이 유니크 키 충돌(500)을 낼 수 있음
