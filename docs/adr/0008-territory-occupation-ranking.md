# ADR 0008: Territory Occupation and Monthly Ranking

## Status
**Accepted** (2026-11-07)

## Context

타임라인 위치 기록(ADR 0007)을 바탕으로, 사용자가 시군구에 머문 누적 시간으로 그 지역을 '점령'하고 지역별 월간 순위와 포인트를 주는 기능이 필요하다.
결정해야 할 것:
- 좌표가 어느 시군구인지 어떻게 판정할지
- 어떤 시간을 점령 시간으로 셀지
- 순위 집계를 어떻게 저장할지
- 포인트를 언제 줄지

## Decision

1. **시군구 판정: 카카오 coord2regioncode + 격자 캐시.** 좌표를 소수점 3자리(약 100m) 격자로 묶어 결과를 `territory_region_cells` 에 저장한다.
   법정동(B) 코드 앞 5자리를 시군구 ID 로 쓴다. 이 값은 `regions.code + region_subdivisions.code` 와 같다(예: 11560 영등포구).
   지역 밖(바다, 코드 `90000`)도 캐시한다. 호출이 실패하면 캐시하지 않고, 그 배치의 남은 호출을 멈춘 뒤 다음 재계산 때 다시 시도한다.
2. **점령 시간: 구 안에 있던 모든 시간.** 연속된 두 위치 기록이 같은 시군구이고 간격이 `territory.max-gap`(기본 3분) 이하이면 그 간격을 센다.
   시군구가 바뀌는 간격, 오래 끊긴 간격, 자정을 넘는 간격은 세지 않는다. 1분 수집 기준으로 잃는 시간은 경계마다 최대 1분이다.
3. **집계: 사용자 x 시군구 x 날짜(`territory_daily_stays`)를 위치 기록에서 다시 계산한다.** 위치 기록이 저장되거나 삭제되면 타임라인이 `TimelinePointsChangedEvent` 를 보낸다.
   그 날짜를 같은 트랜잭션에서 다시 계산하므로, 오프라인 업로드나 순서가 섞인 업로드에도 결과가 같다. 월간 순위와 누적 시간은 이 테이블의 합이다.
4. **포인트: 전체 점령 시간이 `reward-unit`(기본 1시간)을 넘길 때마다 `reward-points`(기본 100P)를 준다.** `point_transactions` 원장에 `OCCUPATION:n` 키로 남겨 같은 보상을 두 번 주지 않는다.
   위치 기록을 지워도 포인트는 회수하지 않는다.
5. **순위:** 같은 시간은 같은 순위이고 다음 순위는 건너뛴다(1, 1, 3). 응답에는 닉네임만 담고 사용자 ID 는 담지 않는다.

화면 캡처와 다른 점: `monthlyRankedStaySeconds` 는 `monthlyStaySeconds` 로 바꿨다. 현재 방문에 `live`(미확인 여부)를 추가했다. 포인트 진행은 시군구별이 아니라 전체 점령 시간 기준이다.

## Rationale

- 카카오는 이미 연동되어 있다. 격자 캐시를 쓰면 같은 동네를 반복해서 다녀도 호출이 거의 늘지 않는다. 경계 파일을 관리할 필요도 없다.
- 날짜 단위로 다시 계산하면 증분 갱신의 순서 문제가 없다. 하루 최대 1440개 기록이라 비용도 작다.
- 원장과 고유 키를 쓰면 같은 업로드를 다시 보내도 포인트가 늘지 않는다.

## Consequences

### 긍정적 영향
- 설정(max-gap, reward-unit, reward-points)만으로 정책을 바꿀 수 있음
- 지역 ID 체계(KR / 시도 / 시군구)가 기존 지역 테이블과 같음

### 부정적 영향
- 처음 가는 격자는 업로드 중에 카카오를 호출해서 응답이 느려질 수 있음
- 월간 순위는 조회할 때마다 그 시군구의 그달 행을 합산함. 사용자가 많아지면 월별 집계 테이블이나 Redis 정렬 집합이 필요함
- 격자 경계 근처에서는 시군구 판정이 100m 정도 틀릴 수 있음
- 같은 사용자의 동시 업로드는 고유 키 충돌을 낼 수 있음 (ADR 0007과 같음)
